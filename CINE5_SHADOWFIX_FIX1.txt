F1 (MUST-FIX) — make rig-vs-world shadow-slot ranking CATEGORICAL, not a finite numeric base
=============================================================================
The recent fix set rig emitters to mSpotLightPriority = 1e9 + r^3 (llvovolume.cpp updateSpotLightPriority,
the isCineRigEmitter() branch). TWO defects:
 (a) NOT ROBUST: calcPixelArea scales ~ (window_height / FOV)^2; at the 5-degree min FOV on a 1440p+
     display a nearby large WORLD projector's pixel-area priority can EXCEED 1e9 and still evict a rig
     projector — reproducing the "zoom to activate shadows" bug the branch was meant to kill.
 (b) ORDERING LOST: an F32 near 1e9 has ~64-unit ULP, so distinct rig radii (r^3 = 35.9 vs 57.1)
     collapse to the same stored priority; with >6 rig projectors the winners become traversal-order
     dependent, not radius-dependent.

FIX (two parts):
 1. llvovolume.cpp updateSpotLightPriority: for isCineRigEmitter(), set mSpotLightPriority = r * r * r
    (world-size, camera-independent) — DROP the 1e9 base entirely. This restores clean r^3 ordering
    among rig lights and removes the camera dependence. (Keep it gated on isCineRigEmitter(); non-rig
    and the existing stable_spots/pixel-area paths stay byte-identical.)
 2. pipeline.cpp setupSpotLight — the spot-shadow slot AUCTION/ranking (the m_pri > pri comparison that
    fills mTargetShadowSpotLight[], ~the block guarded by !gCubeSnapshot && !sPrismLensRender &&
    !isProjectorShadowSuppressed). Make the comparison CATEGORICAL: a candidate that isCineRigEmitter()
    outranks any NON-rig incumbent regardless of numeric priority; a non-rig candidate never displaces a
    rig incumbent; when both candidate and incumbent are the same kind (both rig OR both non-rig),
    compare numeric priority EXACTLY as today. Net effect: enabled rig projectors deterministically hold
    up to 6 slots (the largest r^3 among them win when >6), and world projectors fill any remaining
    slots by their existing pixel-area priority.
 3. Keep the applyFrame projector->updateSpotLightPriority() seed (still needed so a fresh projector has

F3 (SHOULD-FIX) — ratio-locked FILL EV must equal KEY EV - stops even at the EV floor
=============================================================================
alcinelightrigmodel.cpp (~the mRatioLock block): out[1].mEV = clamp(out[0].mEV - mRatioStops, MIN_EV,
MAX_EV). For the reachable input KEY EV = -20, ratio = 5 stops, the spec is fill EV = -25, but the clamp
to MIN_EV returns -20 — the ratio is silently NOT honored, and with a positive master EV the fill can be
up to 32x brighter than the requested ratio.
FIX: honor the ratio across the whole selectable domain. Preferred: preserve the derived fill EV through
the render chain (do not clamp the ratio-derived value to the same MIN_EV floor used for a user-entered
EV; the derived value is a relative offset from the key and must survive). If a floor is required for
numerical safety, widen it so KEY_EV_MIN - MAX_RATIO_STOPS is representable, OR constrain the exposed
key-EV / ratio-stops domain so every selectable combination stays representable. Add a BOUNDARY TUT test:
key EV at its minimum + max ratio stops yields exactly key - stops (not clamped), and ratio-lock OFF
leaves fill EV byte-identical.
