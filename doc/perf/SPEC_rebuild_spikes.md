## Decision and evidence

External hardware records the live output. Preserve geometry, colour, alpha, materials, animation, shadows and reflections on the frame where they should change. At 30 fps on a 60 Hz display, missing the 33.33 ms delivery deadline can hold the image for another refresh. Lower quality, skipped updates and stale visible content are unacceptable. A CPU timing improvement alone does not establish smooth recorded output.

**Proven:** full group regeneration and batched VBO uploads account for the large first-shadow `postSort`s. **Not proven:** which objects/mutations produce their burst cadence, or whether upload time is primarily implicit GPU synchronization. Instrument those two questions before selecting an implementation.

## What causes the rebuild, and why shadows pay

The code proves a route from changed TE RGB to full regeneration:

`LLPrimitive` TE unpack invokes virtual setters (`indra/llprimitive/llprimitive.cpp:1449,1466,1574,1591`) → `LLVOVolume::setTEColor` (`NV/llvovolume.cpp:2494`) → `mColorChanged`, `REBUILD_COLOR`, `dirtyMesh()` → `LLViewerObject::dirtyMesh` (`NV/llviewerobject.cpp:7406`) requests **REBUILD_ALL, including REBUILD_VOLUME** (`NV/lldrawable.h:259–263`) → `updateGeom` drains drawable queue (`NV/pipeline.cpp:4869`) → `LLVOVolume::updateGeometry:2307` calls `dirtySpatialGroup()` → `GEOM_DIRTY` and group enqueue (`NV/llviewerobject.cpp:7393`). Thus an RGB change can rebuild neighbouring faces as well as the changed face. Unchanged colours are already guarded. Scripted club prims fit this route, but the capture contains no mutation/object provenance establishing that origin or a 0.3–0.5 s timer.

`renderShadow` calls `stateSort` (`NV/pipeline.cpp:28890`), which calls `postSort` (`:5286`). Unless `gCubeSnapshot`, `postSort:5684–5702` rebuilds drawable groups and drains the **global** priority queue. `rebuildPriorityGroups:4828–4850` rebuilds every queued group without a time budget or shadow-frustum restriction; later passes see an emptied queue. The drain has no periodic timer. Moving it earlier merely relocates the bill.

`genDrawInfo` allocates buffers and force-fills faces (`NV/llvovolume.cpp:7490–7555`). `LLSpatialGroup::rebuildGeom` queues pending mesh work (`NV/llspatialpartition.cpp:325–334`); `postSort:5840–5849` later calls `rebuildMesh`. Its flush (`NV/llvovolume.cpp:6958`) drains **all** staged buffers (`VB:1025`), not just that group's buffers. Attribute upload cost to buffer producers, not solely to the group surrounding the flush zone.

## Why uploads are expensive: test the mechanism

Windows uses `LLDefaultVBOPool` (`VB:948–960`). Its “mapped” pointers are aligned **CPU allocations**; map calls tag dirty byte ranges (`VB:1285–1356`), and `_unmapBuffer` merges ranges before `flush_vbo` calls `glBufferSubData` (`VB:1365–1538`). There is no GL mapping call in this path. `RenderVBOMappingDisable` has an XML definition (`NV/app_settings/settings.xml:22452`) but no active source reader; toggling it is not a useful experiment here.

The pool creates storage on a miss (`VB:442–475`), but on a hit returns an old GL name and CPU block without orphaning or checking GPU completion (`:477–488`). Free stores an age (`:498–527`); allocation picks the oldest entry, yet enforces no retirement delay/fence. Five-second cleanup (`:532–577`) is eviction, not synchronization. An application reference becoming unused does not prove submitted GPU reads finished.

**Hypothesis:** reusing or partially updating in-flight storage forces driver synchronization. Khronos documents this hazard and storage orphaning as a possible remedy in [Buffer Object Streaming](https://wikis.khronos.org/opengl/Buffer_Object_Streaming). Driver allocation, residency pressure, CPU preemption and command submission also remain possible. CPU zone time does not isolate DMA or a driver wait.

The quoted 0.09–0.17 ms is not the cost of every upload: `glBufferSubData` averages **0.09175 ms**, median **0.01968**, p99 **0.83462**, max **3.56698** within these events. Approximately 0.168 ms is the mean **vertex-unmap zone**, potentially containing several uploads. Measure the distribution and bytes, not just means.

### Minimal diagnostic slice, before fixes

One opt-in `PerfRebuildDiagnostics=false` gate, bounded main-thread records, static Tracy zones, one summary after capture. No per-face formatted logging, hot-path UUID strings, synchronous readbacks or `glFinish`.

- Tag **actual changed mutations**, plus attempt/no-op counts, with reason: RGB, alpha, texture, UV/material, generic volume, mesh/LOD, flexi, texture-animation transition, attachment, partition/alpha-sort, light RGB, override setter, unknown. Capture remote-TE versus local-feature origin at source. Carry reason bits and object/TE identity across drawable queueing to group queueing; a temporary scope tag alone does not survive `updateGeom`.
- Hook both `markRebuild` overloads (`NV/pipeline.cpp:5126,5140`), group dirty transitions and the drains. Distinguish requests, new enqueues, coalesced requests and executed builds. Retain first/latest frame, group lifetime ID, flags before/after, triggering object versus all members rebuilt, queue depth and render/capture kind. Keep bounded top-object summaries and an overflow/unknown count; invalidate attribution if provenance is missing. Never dereference expired pointers.
- At `VB:442,498,1365,1415`, associate GL name plus allocation generation/lease, producer groups, target, logical size, **rounded capacity**, upload offset/bytes, pool hit/miss, free age and last-use frame. Count bytes/calls/time by cause. Add `rebuild reason`, `pool reuse`, `orphan`, and direct driver-call zones; preserve the existing parent zones for comparisons.
- Sample a fence **after the last submitted consumer**, including shadows, beauty, masks and probes; poll with zero timeout before reuse/overwrite. [Khronos Sync Object](https://wikis.khronos.org/opengl/Sync_Object) describes this completion test. A frame fence can conservatively cover preceding consumers; age alone cannot certify safety. Compare matched-size uploads to busy versus signalled/fresh storage. Unsignalled correlation plus a same-work fresh/orphan A/B improvement supports the sync hypothesis; equal costs leave it inconclusive. Report diagnostic overhead with the gate off/on.

## Ranked implementation slices

Savings below are **opportunity ceilings, not measured gains**, across the selected 15 events in 20 s. Their 282.5 ms total averages 18.8 ms per affected event; gains overlap and must never be added. Every slice uses the common capture/visual procedure below, changes one mechanism at a time, and defaults to stock when its switch is off.

**Separate correctness prerequisite when Force Mask is active:** stabilize authored alpha classification from TE/material/texture inputs, checking parity with `getPoolTypeFromTE` (`NV/pipeline.cpp:3786–3839`), before trusting policy-based fast-path eligibility. ## Open questions (four)

2. Do slow uploads correlate with incomplete GPU consumers, and does fresh/orphaned storage remove end-to-end latency at acceptable peak VRAM on this driver?
3. Were Force Mask/Actor Mask/Cine Rig/live probes active, and do their own mutations or policy inconsistencies contribute measurable rebuilds rather than only GPU pressure?
4. What explains the overlapping `doFrame` scopes, and which frame/presentation sequence accurately predicts refresh repeats in the external recording?
