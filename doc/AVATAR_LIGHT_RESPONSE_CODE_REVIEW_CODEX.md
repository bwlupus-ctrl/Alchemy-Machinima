- **P1 — Legacy Tame changes diffuse lighting.** `app_settings/shaders/class1/alchemy/avatarLightResponseF.glsl:100` scales `env`; `class3/deferred/fullbrightShinyF.glsl:150` does likewise. But `app_settings/shaders/class3/deferred/reflectionProbeF.glsl:959` blends the existing color with reflection using that same env value, after also multiplying reflection by env and env-dependent Fresnel. With black reflection and authored env = 0.5, the original output is 0.5C; Tame 100% produces C. Diffuse doubles, and intermediate reflection attenuation is nonlinear. The class2 fallback also blends by env. This is a design flaw, not merely implementation drift: preserve authored mixing/Fresnel and attenuate the evaluated reflection contribution separately.

- **P1 — Self settings disappear on relog.** `llstartup.cpp:1207` loads during `STATE_LOGIN_CLEANUP`, before authentication assigns `gAgentID` at `llstartup.cpp:3881`. Saved self entries use the literal `"self"`; `alavatarlightresponse.cpp:99` resolves it to the still-null ID, and `:620` rejects it. Every saved self adjustment or explicit identity is lost on fresh startup; a subsequent save removes it from disk. Load after the authenticated ID exists, or defer self-key resolution.

- **P2 — Account state survives failed-login account switching.** `alavatarlightresponse.cpp:572` returns for a missing file without clearing the singleton store; disabled persistence and parse failures similarly retain it. Load account A during login cleanup, fail login, then select account B without a response file: A's resident entries remain active and can be saved into B's file. Reset account-owned state and invalidate the table when changing accounts, independently of whether the new file exists or parses successfully.

- **P2 — Worn-animesh menu targets the wearer.** `alviewermenu.cpp:1007` uses `find_avatar_from_object()`, whose attachment branch at `llviewermenu.cpp:9384` walks directly to the wearer. Thus right-clicking a worn pet opens the wearer's response row; editing it changes the wearer and inherited dependents. Resolve the object's control avatar first, as the existing skeleton-reset resolver does at `llviewermenu.cpp:7012`.

- **P2 — Unknown visibility is reported as success.** `alfloateravatarlightresponse.cpp:399` treats `mVisible != 0` as visible, although overlay clones deliberately retain -1 (`alavatarlightresponse.cpp:415`). The logger repeats this at `:514`. An upload before palette failure or without visible output can therefore produce a green dot and `UPLOADED` verdict despite visibility never being established. Require `mVisible == 1`; retain amber/inconclusive for unknown visibility until proxy visibility is supplied.
